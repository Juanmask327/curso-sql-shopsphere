# Auditoría de seguridad — ShopSphere SQL Platform

**Fecha:** 2026-06-18
**Autor:** Dr. Alejandro Vega (security-hardener)
**Alcance:** auditoría de dependencias (`npm audit`) en los tres directorios del proyecto + inspección de código del backend (`backend/src/`).
**Estándares de referencia:** OWASP Top 10 (2021), CWE, NIST SP 800-53.

---

## Resumen ejecutivo

La postura de seguridad de la plataforma es **sólida**. La auditoría de dependencias no reveló ninguna vulnerabilidad explotable en producción: los 24 CVEs de Next.js ya fueron remediados con la actualización a `15.5.19`, y el resto de los hallazgos son o bien dependencias de desarrollo (sin superficie en el contenedor Docker de producción), o vectores cuya explotabilidad en este codebase es prácticamente nula (drizzle-orm, uuid). La inspección de código confirmó que los controles de seguridad endurecidos en pases previos (CORS fail-closed, headers, validación de `JWT_SECRET`, IDOR del diagnóstico, sandbox del worker, backpressure del pool) siguen correctamente cableados. No se detectaron vulnerabilidades nuevas de severidad CRITICAL ni HIGH. El único hallazgo de dependencias pendiente que merece seguimiento es `postcss < 8.5.10` (XSS en CSS stringify), aceptado como riesgo residual por ser dependencia transitiva interna de Next.js sin fix disponible sin degradar el framework.

---

# Sección 1 — Auditoría de dependencias (`npm audit`)

## Metodología

Se corrió `npm audit` en `frontend/`, `backend/` y la raíz del monorepo. Cada hallazgo se clasificó según la **severidad real en este codebase** (explotabilidad efectiva) frente a la **severidad reportada** por el advisory, considerando si la dependencia está en el árbol de runtime de producción o solo en `devDependencies`.

## Frontend

| Paquete | Advisory | Severidad reportada | Severidad real | Estado |
|---|---|---|---|---|
| `next` (15.3.2) | 24 CVEs: SSRF, cache poisoning, XSS, DoS | CRITICAL/HIGH | CRITICAL/HIGH | **RESUELTO** — actualizado a `15.5.19` |
| `postcss` (< 8.5.10) | XSS en CSS stringify (parsing de CSS no confiable) | MODERATE | BAJA | **ACEPTADO** (riesgo residual) |

### Detalle — next (RESUELTO)
La cadena de 24 CVEs en `next@15.3.2` incluía Server-Side Request Forgery, envenenamiento de caché, Cross-Site Scripting y Denial of Service en el servidor de renderizado. Todos quedan cubiertos por la actualización a `15.5.19`.
- **Acción tomada:** bump de `next` a `15.5.19` en `frontend/package.json`.
- **Verificación:** `cd frontend && npm audit --audit-level=high` debe reportar 0 vulnerabilidades high/critical atribuibles a `next`. Confirmar `npm run build` y `npm run lint` siguen pasando.

### Detalle — postcss (ACEPTADO)
`postcss < 8.5.10` tiene un XSS en la etapa de stringify cuando procesa CSS de una fuente no confiable.
- **Por qué la severidad real es baja:** `postcss` entra como dependencia transitiva interna de Next.js. La plataforma no procesa CSS provisto por el usuario a través de postcss en runtime; solo compila CSS propio en build time. El vector de XSS requiere alimentar CSS atacante al stringifier, lo que no ocurre en el flujo de la aplicación.
- **Por qué se acepta:** no existe un fix que no implique degradar la versión de Next.js (lo que reintroduciría los 24 CVEs anteriores, de severidad mucho mayor). Subir Next.js cuando publiquen una versión que fije la dependencia transitiva resolverá esto.
- **Seguimiento:** revisar en cada bump de Next.js si `postcss` quedó >= 8.5.10.

## Backend

| Paquete | Advisory | Severidad reportada | Severidad real | Estado |
|---|---|---|---|---|
| `drizzle-orm` (< 0.45.2) | GHSA-gpj5-g38j-94v9 — SQL injection en identificadores | HIGH | DESPRECIABLE | **ANALIZADO** — no explotable |
| `esbuild` (≤ 0.24.2) | GHSA-67mh-4wv8-2f99 — dev server accesible cross-origin | MODERATE | NO APLICA | **NO APLICA en prod** |
| `uuid` (< 11.1.1) | GHSA-w5hq-g745-h8pq — buffer bounds check | LOW | BAJA | **ANALIZADO** — baja explotabilidad |
| `vitest` / `vite` / `drizzle-kit` | transitivos de `esbuild` | MODERATE | NO APLICA | **NO APLICA en prod** (solo dev) |

### Detalle — drizzle-orm (ANALIZADO, no explotable)
El advisory describe una inyección SQL cuando se pasa input controlado por el atacante como **identificador** SQL (nombre de tabla/columna).
- **Por qué no es explotable aquí:** se revisó todo el uso de `sql` y de identificadores dinámicos en `backend/src/`. El código nunca construye identificadores SQL a partir de input de usuario; todos los identificadores son referencias estáticas de schema TypeScript (`users.id`, `userExerciseProgress.attemptsCount`, etc.). Las plantillas `sql\`...\`` que existen interpolan **objetos de columna de Drizzle** (identificadores parametrizados por el ORM) o **valores enlazados** (`${xpEarned}`), nunca strings de usuario. No hay ningún `sql.raw()` ni concatenación de strings en queries.
- **Acción recomendada:** actualizar `drizzle-orm` a `>= 0.45.2` en el próximo ciclo de mantenimiento por higiene (defensa en profundidad), sin urgencia.

### Detalle — esbuild y transitivos (NO APLICA en producción)
GHSA-67mh-4wv8-2f99 permite que cualquier sitio web envíe peticiones al dev server de esbuild y lea la respuesta.
- **Por qué no aplica:** `esbuild` (y sus dependientes `vitest`, `vite`, `drizzle-kit`) son **devDependencies**. El dev server de esbuild no corre en el contenedor Docker de producción, que ejecuta el bundle compilado bajo Node.js 22. La superficie de ataque solo existe en la máquina de un desarrollador con el dev server expuesto a la red.
- **Acción recomendada:** ninguna obligatoria. Mantener las devDependencies actualizadas en el ciclo normal.

### Detalle — uuid (ANALIZADO, baja explotabilidad)
GHSA-w5hq-g745-h8pq — falta de validación de límites de buffer en `uuid < 11.1.1`.
- **Por qué la severidad real es baja:** `uuid` entra como dependencia transitiva de `google-auth-library`. No se invoca con buffers controlados por el atacante en el flujo de la aplicación. La generación de identificadores propia del backend usa `crypto.randomUUID()` (nativo de Node) y `crypto.randomBytes()`, no este paquete.
- **Acción recomendada:** se resolverá sola al actualizar `google-auth-library`; sin urgencia.

## Problema de entorno local

- **Síntoma:** `npm audit fix` no puede correr localmente.
- **Causa raíz:** la máquina local tiene **Node.js v24**, mientras que Docker usa **Node.js v22**. `better-sqlite3@9.6.0` no publica binario precompilado (prebuilt) para Node v24 en Windows, por lo que la instalación intenta compilar desde fuente y falla, abortando el `npm audit fix`.
- **Impacto:** ninguno sobre la seguridad de producción (el contenedor usa v22, donde el prebuilt existe). Es una fricción de tooling local.
- **Recomendaciones:**
  1. Usar Node.js v22 localmente (alinear con Docker) vía `nvm`/`fnm` y un archivo `.nvmrc`/`engines` con la versión fijada.
  2. Alternativamente, correr `npm audit`/`npm audit fix` dentro del contenedor: `docker exec shopsphere-backend npm audit`.
  3. Evaluar actualizar `better-sqlite3` a una versión con prebuilt para Node v24, validando antes que no rompa el worker del playground.

## Resumen de pendientes (sección dependencias)

| `postcss < 8.5.10` (vía Next.js) | BAJA | Seguimiento en cada bump de Next.js |

# Sección 2 — Inspección de código (`backend/src/`)

Revisión manual de la superficie de mayor riesgo: `app.ts`, módulo de autenticación completo (servicio, rutas, controlador, schemas, OAuth), playground (servicio, worker, worker-pool, rutas), validación, middleware de auth, y rutas de users/certificates/diagnostic.

## Hallazgos

**No se detectaron vulnerabilidades nuevas de severidad CRITICAL ni HIGH.** Los controles endurecidos en pases anteriores siguen vigentes. A continuación se documenta la evidencia que confirma cada control y dos observaciones de severidad informativa/baja.

### Controles verificados como correctos (evidencia)

**[OK] Inyección SQL — no presente**
`backend/src/modules/playground/playground.service.ts`, `validation.service.ts`, `auth.service.ts`, `shared/db/schema.ts`
Todo el acceso a PostgreSQL usa el query builder de Drizzle con valores enlazados. Las plantillas `sql\`...\`` interpolan exclusivamente objetos de columna de Drizzle (identificadores controlados por el ORM) o valores parametrizados — nunca strings de usuario. No existe `sql.raw()` ni concatenación de strings SQL. CWE-89 no aplica.

**[OK] Aislamiento del playground (RNF-05) — sandbox sólido**
`backend/src/modules/playground/worker.ts`
La SQLite del dataset se abre `readonly: true` + `pragma query_only = ON` (defensa en profundidad). Las sentencias no de solo-lectura se rechazan vía `stmt.readonly === false`. La query del estudiante se ejecuta en un Worker Thread aislado que **no hereda el env completo** del proceso (`worker-pool.ts` pasa solo `NODE_ENV`), lo que reduce la superficie de exfiltración de secretos. better-sqlite3 deshabilita por defecto la carga de extensiones y el prepare multi-statement, por lo que ATTACH / `load_extension` / `readfile` / stacked-queries no son alcanzables.

**[OK] DoS por CPU/memoria en el playground — acotado**
`backend/src/modules/playground/worker.ts` + `worker-pool.ts`
- Memoria: `stmt.iterate()` con tope duro `MAX_SCAN_ROWS = 50_000` y respuesta limitada a 1000 filas — un producto cartesiano masivo no puede agotar la RAM del worker (CWE-400).
- Tiempo: el `runOnWorker` aplica un timeout por query que **mata el worker** (`worker.terminate()`) desde el hilo principal; no es evadible porque no depende del worker bloqueado. El worker crasheado se reemplaza automáticamente.
- Tamaño de payload: `playground.service.ts` rechaza queries > 4096 bytes (`QUERY_TOO_LARGE`) **antes** de tocar el rate limit o el pool.
- Backpressure: `worker-pool.ts` con `maxQueue = poolSize * 10` lanza `QueueFullError` → 503 `PLAYGROUND_AT_CAPACITY`.

**[OK] Rate limiting — presente y en capas**
- Global por IP: 100 req/min (`app.ts`), con `keyGenerator` basado en `request.ip` que respeta `trustProxy` (no lee `x-forwarded-for` crudo → no falsificable salvo detrás de proxy de confianza).
- Playground: 60 validaciones/min por **usuario** vía Redis sliding window (`playground.service.ts`), más backup de 120/min por IP en la ruta.
- Login: 5 intentos/15 min por IP (`auth.routes.ts`). Register 10/h, refresh 20/15min, reset/verify con sus propios límites. Los códigos de verificación/reset tienen `MAX_CODE_ATTEMPTS = 5` y cooldown de reenvío.

**[OK] Autenticación / JWT — configuración robusta**
- `JWT_SECRET` validado en arranque: crash si < 64 chars. `SESSION_COOKIE_SECRET` crash si < 32 (`app.ts`). Cumple las reglas del proyecto.
- JWT firmado con HS256 explícito; access token de 15 min, refresh opaco de 256 bits cuyo **hash SHA-256** es lo único persistido (robo de DB no revela tokens).
- Refresh token rotation con revocación transaccional del token viejo (`auth.service.ts`).
- `authGuard` verifica firma + `type === 'access'` (impide reusar refresh como access) + revocación de sesión en Redis con fallback a DB.
- Login con bcrypt (rounds 12 en prod) y comparación con hash dummy cuando el usuario no existe → mitiga timing attacks de enumeración (CWE-208). Cuenta inactiva devuelve el mismo error genérico.
- Enumeración de cuentas mitigada también en `forgot-password` / `resend-verification` (siempre 204, no revelan existencia).

**[OK] Google OAuth — state validado (anti-CSRF)**
`backend/src/modules/auth/auth.controller.ts`
El `state` se genera con `randomBytes(16)` (CSPRNG), se guarda en Redis con TTL 10 min, y en el callback se valida y se **consume** (`redis.del`) antes de intercambiar el code. El `id_token` se verifica con `audience = GOOGLE_CLIENT_ID`. Los tokens se devuelven al frontend en el **fragment** de la URL (`#access=...`), que no llega al servidor ni aparece en access logs. CWE-352 cubierto.

**[OK] Control de acceso / IDOR — sin referencias directas inseguras**
Todos los endpoints de datos de usuario derivan la identidad de `request.user.sub` (token), nunca de body/params: `/users/me/dashboard`, `/users/me/exercises`, `/users/me/certificates`, `PATCH /users/me/profile`. Las rutas admin están detrás de `authGuard + adminGuard`. El IDOR previo en `POST /diagnostic/submit` (aceptaba `user_id` del body) sigue corregido: la ruta es pública pero **no persiste**; la persistencia solo ocurre en `POST /diagnostic/save-result` autenticado con `req.user.sub`. Los handlers admin impiden auto-cambio de rol y auto-desactivación.

**[OK] Headers de seguridad — presentes**
`app.ts` (hook `onSend`): `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-site`, CSP restrictiva (`default-src 'none'`), `Permissions-Policy`, HSTS solo en prod, y se remueve `X-Powered-By`. El hook excluye `/docs` para no romper la CSP de Swagger UI.

**[OK] CORS — fail-closed**
`app.ts`: lee `ALLOWED_ORIGINS` (fallback `CORS_ORIGIN`). En producción sin allowlist deniega todos los orígenes cross-site (no cae a `*`). `credentials: true`, headers permitidos acotados.

**[OK] Manejo de secretos / errores**
- `.gitignore` excluye `.env`, `.env.local`, `.env.*.local` y `data/*.db`. Sin credenciales hardcodeadas en fuente.
- El error handler global no filtra stack traces al cliente en producción (mensaje genérico para 500; detalle solo en no-prod).
- En prod se prohíben niveles de log verbosos (trace/debug/silent) para no filtrar PII/tokens/queries.

### Observaciones (informativas / baja severidad)

**[INFO] `/metrics` sin autenticación de aplicación**
`backend/src/app.ts` (línea ~473)
El endpoint `GET /metrics` (Prometheus) está siempre habilitado y sin auth. Expone métricas operativas (latencias, conteos, estado del worker pool) — no datos de usuario ni secretos. El propio comentario en el código indica que en producción debe protegerse a nivel de red/firewall.
- **Impacto:** fuga menor de información operativa si el puerto del backend queda expuesto públicamente sin firewall. No expone PII ni credenciales.
- **Recomendación (sin cambio de lógica):** restringir el acceso a `/metrics` por red en el despliegue (allowlist de IP del scraper de Prometheus / network policy), o gatearlo tras un token de scrape. No requiere cambios de código si la infraestructura ya lo aísla. Documentar en `docs/runbook.md`.
- **Severidad:** LOW / informativa.

**[INFO] `API_INTERNAL_SECRET` declarado pero sin uso en fuente**
Presente en `.env`/`.env.example` pero no referenciado en `backend/src/`. Es un secreto **dormido**, no un vector activo. Recomendación: si no se va a usar, removerlo del `.env.example` para evitar confusión; si es para una feature futura, documentarlo. Severidad: informativa.

## Conclusión de la inspección

El backend mantiene una postura defensiva consistente: validación en el boundary (Ajv + Zod), parametrización total de SQL, aislamiento real del playground con límites de CPU/memoria/tamaño, autenticación con rotación de refresh tokens y revocación, OAuth con state anti-CSRF, control de acceso scopeado al token, y headers + CORS fail-closed. No se identificaron vulnerabilidades nuevas accionables de severidad media o superior. Las dos observaciones son de naturaleza operativa/informativa y no representan un vector explotable en la configuración de despliegue documentada.

## Riesgo residual

1. **`postcss < 8.5.10`** — XSS en CSS stringify, no explotable en el flujo actual, sin fix sin degradar Next.js. Seguimiento en cada bump del framework.
2. **`/metrics` público a nivel de aplicación** — depende de aislamiento de red en el despliegue; sin él, fuga de métricas operativas (no PII).
3. **Dependencias transitivas dev (esbuild y derivados)** — sin superficie en producción; mantener actualizadas por higiene.
4. **Desalineación Node v24 (local) vs v22 (Docker)** — impide `npm audit fix` local; resolver con `.nvmrc`/`engines` o auditar dentro del contenedor.
5. **Endurecimientos que requieren cambio arquitectónico (fuera de alcance de este pase):** considerar a futuro un sandbox a nivel de proceso/contenedor adicional para el worker SQLite (defensa en profundidad ante un eventual 0-day de better-sqlite3) y revocación masiva de sesiones ante detección de reuso de refresh token robado (hoy solo error genérico). Ambos son mejoras, no vulnerabilidades.
